# E12：评分口径与导出格式的重大不一致（必须马上改）

日期：2026-10-18。发现于官方评测须知与本地 GT 对照核查。0 API、0 训练、未改 GT。

## 结论

**官方把「位号（Name）」列为所有元件类型的 TP 必需条件；我们本地评分器只对 box/ic 检查 Name。**
按官方字面口径重评，当前导出配置会从 23.09% 掉到 **2.57%**——因为无源器件的 `Name` 我们导出成了 `null`。

| 预测版本 | 本地现状规则（Name 只比 box/ic） | 官方字面规则（所有类型都比 Name） |
|---|---:|---:|
| `submitted`（当前导出的正式配置） | 23.09%（TP 170） | **2.57%（TP 19）** |
| `submitted_name_key`（无源器件 Name 填成位号） | 23.09%（TP 170） | **20.36%（TP 148）** |
| `name_key_no_filter`（同上 + 不过滤未分类） | 23.35%（TP 170） | 20.60%（TP 148） |

## 依据

1. **官方须知原文**：「元件ID匹配 / 类型完全匹配 / **位号完全匹配（Name字段）** / 参数值完全匹配 / bbox」并列。
2. **官方 GT 的实际内容**（`0001-KiCad.json`）：91 个元件里 **87 个 `Name` 等于 key（位号）**；IC 的 `Name` 是型号（`U1 → RP2350B`、`u2 → RM2`）。
3. **non404 的评分代理**（`accuracy_proxy._official_components_match`）也是**对所有类型比较 Name**，再对 r/c 加比 value。

三条独立证据一致指向：**比较 Name 是全局规则，我们本地评分器才是那个例外。**

## 立即修复（导出层，一行）

对 `type` 不是 `box`/`ic` 的元件，导出时 `Name = 位号（key）`：

```python
if kind not in {"box", "ic"}:
    name = key
```

改完后按官方口径约 **20.36%**（含未命名恢复 + 不提交未解析），而不是现在汇报的 24.71%。

## 连带影响

- **过去两天所有「严格 ComponentF1」数字都偏乐观**（17.42 / 24.71 / 21.87 等），因为本地评分器宽松。需要用修正后的评分器重算一遍，并统一改口径说明。
- IC 仍有 22 个 TP 在严格口径下丢失，原因是型号（`Name`）没提取对或没提取到——这是**型号识别**问题，与位号识别是两条线。
- 这说明 `Name` 字段实际承担两个语义：无源器件=位号，IC/模块=型号。导出时必须按类型分流。
