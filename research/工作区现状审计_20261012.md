## 实际主流程

核心入口 non404/show_up/contest6/run_q123_pipeline.py 分 prepare 和 finish：

1. prepare 读取预先生成的 OCR 结果，加载锁定 YOLO 与 U-Net 权重并验证哈希。
2. YOLO 输出元件框与类别；原图几何扫描产生 pin 候选。
3. U-Net 分割导线，进行文字抑制、边界过滤、骨架与图构建。
4. finish 将原图和候选证据交给语义模型，判断字段身份、pin 有效性、交叉点和标签。
5. q123_integration.py 将语义决策与几何结果组装，使用 UnionFind、方向/距离/阻挡检查和网络标签合并产生 nets。
6. score_q123_pipeline.py 独立读取 GT 评分，核心是 accuracy_proxy.py，自称本地公开规则近似，不是主办方评分器。

现有优点：感知/语义/评分分离；输出校验；不允许语义模型覆盖几何坐标；保存哈希、请求绑定、阶段证据与断点续跑检查。

## 工程风险

1. 不确定交叉默认连接。edge_groups 只在 connected 严格为 False 时拆分；null 或缺失都会走合并。需要显式定义不确定策略并用真实负例评估，不建议简单全部改成断开。
2. 输入命名假设不统一。discover_images 允许非数字文件名；finish 用 int(p.parent.name) 排序。因此使用旧公开数据的 0001-KiCad 等文件名可能在 finish 阶段失败，应先统一 case_id 或改成一致的自然排序。
3. 评分批处理要求每张 GT 都有预测，缺失时抛错；若用于模拟比赛，应额外按完整案例列表补零并报告完成率，不能只平均成功案例。
4. 网络标签按字符串合并，没有显式层次作用域。扩展到多页或层次原理图前需要引入 scope，避免不同局部同名网误合并。
5. API 配置有单请求 timeout，但主入口未见全局两小时截止控制和失败兜底；流式请求的总墙钟时间仍需单独约束。历史报告 token usage 为 null，无法评估真实 Token 成本。
6. 多处 read_text 未指定编码；在 Windows 上应核对编码，特别是中文路径进入 JSON 的场景。
